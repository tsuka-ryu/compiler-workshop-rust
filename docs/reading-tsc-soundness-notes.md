## 1. TAPL Ch 8 (型付き算術式): 進行 + 保存

読んだ日: 2026-11-09

評価規則 (E-IFTRUE など) は第 3 章の図 3-1 (真偽) と図 3-2 (数)。8 章はそこに型付け規則を足した章。

### 前提: 図 3-1 ブール値 (B、型無し) の構文と評価規則

項と値:

```
t ::= true | false | if t then t else t      項
v ::= true | false                           値
```

評価規則 (`t → t'` は「`t` が 1 歩進んで `t'` になる」):

```
(E-IfTrue)   if true then t₂ else t₃  →  t₂

(E-IfFalse)  if false then t₂ else t₃  →  t₃

               t₁ → t₁'
(E-If)  ─────────────────────────────────────────────
        if t₁ then t₂ else t₃  →  if t₁' then t₂ else t₃
```

- E-IfTrue / E-IfFalse: 条件が値 (`true` / `false`) になっているときに、`then` 側 / `else` 側を取り出す
- E-If: 条件がまだ値でないとき、条件の部分だけを 1 歩進める。`then` と `else` は触らない
- 値は `true` と `false` だけ。`if` は値ではないので、`if` は必ず評価が進む (進行の T-IF のケースで使う)

### 前提: 図 3-2 算術式 (NB、型無し) の構文と評価規則

図 3-1 への拡張。項と値に次を足す:

```
t  ::= ... | 0 | succ t | pred t | iszero t     項
v  ::= ... | nv                                 値 (数値も値)
nv ::= 0 | succ nv                               数値
```

評価規則を足す:

```
              t₁ → t₁'
(E-Succ)  ─────────────────────
          succ t₁ → succ t₁'

(E-PredZero)  pred 0 → 0

(E-PredSucc)  pred (succ nv₁) → nv₁

              t₁ → t₁'
(E-Pred)  ─────────────────────
          pred t₁ → pred t₁'

(E-IszeroZero)  iszero 0 → true

(E-IszeroSucc)  iszero (succ nv₁) → false

               t₁ → t₁'
(E-Iszero)  ─────────────────────────
            iszero t₁ → iszero t₁'
```

- `succ`、`pred`、`iszero` は、それぞれ「引数を先に進める規則」(E-Succ、E-Pred、E-Iszero) を持つ。E-If と同じ形
- `pred` と `iszero` は、引数が数値 (`0` か `succ nv`) になって初めて、結果を返す規則が使える
- `nv` は `0` と `succ nv` だけ。`succ true` や `pred false` に当てはまる規則はなく、行き詰まり状態になる
- 進行の T-PRED の場合 (`t₁ : Nat` で値なら `0` か `succ nv₁` なので、E-PredZero か E-PredSucc が使える) は、この図の規則を指している

### 読んだ要点 (本の内容。自分の言葉ではない)

- **8.1 型**: 対象はブール値と数だけの小さな言語。評価の結果は「値」か「行き詰まり状態」(`pred false` のように、どの評価規則も当てはまらない項)。行き詰まりは無意味・間違いのプログラムに当たる。評価せずに行き詰まらないことを言うため、項を `Nat` / `Bool` に分類する。型の分析は**保守的**で、`if true then 0 else false` は実際には行き詰まらないが型なしになる
- **8.2 型付け関係**: 図 8-1・8-2 の規則で `t : T` を定義する。型エラーとは「規則から導出できない」こと。補題 8.2.2 (逆転補題) は規則の逆読みで、部分式の型から全体の型を計算する再帰アルゴリズムがそのまま得られる。定理 8.2.4 (型の一意性): この言語では各項の型は高々 1 つ。第 15 章の部分型で緩む (TS で `Dog` が `Animal` でもあるのと同じ)
- **8.3 安全性 = 進行 + 保存** (本は「安全性」と「健全性」を同義として扱う):
  - 補題 8.3.1 (標準形): `Bool` 型の値は `true` / `false`、`Nat` 型の値は数値だけ。進行の証明で使う
  - 定理 8.3.2 (進行): `t : T` なら、`t` は値であるか、`t → t'` と 1 歩進められる
  - 定理 8.3.3 (保存): `t : T` かつ `t → t'` なら `t' : T`
  - 2 つを合わせると、型が付いた項は行き詰まらない
- **脚注 3**: 部分型を持つ体系では、評価の途中で型が小さくなる (情報が増える) ことがある。保存が「型が同じ」でなく「型が付いたまま」と書かれるのは、この余地のため
- **脚注 4**: 進行・保存を満たさないのに型安全と考えられる言語もある。例: Java を小ステップ形式で書くと保存が失敗する (第 19 章)。ただし大ステップ形式なら失敗しないので、言語の欠陥ではなく**形式化の側の欠陥**と見る。健全性は、評価規則をどう書いたかと切り離せない
- 演習 8.3.6 (主部展開: `t → t'` かつ `t' : T` なら `t : T` か) は未解答。TS で成り立たない例があるか考える

### 定理 8.3.2 (進行) を噛み砕くと

> `t : T` なら、`t` は値であるか、ある `t'` が存在して `t → t'` となる

- `t : T` は「`t` に型が付く」という仮定。型付け規則から導出できたときだけ成り立つ
- `t → t'` は「項 `t` を評価規則で 1 歩書き換えると項 `t'` になる」。書き換わるのは**項**で、型ではない
- 言い換え: 型が付いている項は、値になっているか、評価規則のどれかで次の 1 歩がある。**どの規則も使えず止まる (行き詰まる) ことはない**
- 例: `if (iszero 0) then 0 else (pred 0)` は、E-IF → E-IFTRUE と進んで値 `0` で止まる。`if 0 then 0 else 0` は行き詰まるが、条件が `Nat` なので**そもそも型が付かない**ので、定理の対象外

### 進行の証明: 基底の場合 (T-TRUE、T-FALSE、T-ZERO)

- 導出の最後の規則がこの 3 つなら、`t` は `true`、`false`、`0` という定数そのもの。定数は値の定義に入っているので、「値であるか、進める」の「値である」が成り立つ
- 前提 (部分導出) を持たない規則なので、帰納法の**基底**にあたる。部分式がなく、帰納法の仮定も要らない
- それ以外 (T-IF、T-SUCC、T-PRED、T-ISZERO) は部分式を持つ**帰納の場合**で、帰納法の仮定を使う

### 進行の証明: 帰納の場合 (T-IF)

`t = if t₁ then t₂ else t₃`。導出の最後の規則が T-IF なので、前提 `t₁ : Bool`、`t₂ : T`、`t₃ : T` は規則の形から手に入る。

帰納法の仮定を `t₁` に当てると、`t₁` は値であるか、`t₁ → t₁'` と進める。

| `t₁` | 根拠 | 使う規則 | `t` の行き先 |
|---|---|---|---|
| 値で `true` | 標準形補題 (`Bool` 型の値は `true` か `false`) | E-IFTRUE | `t₂` |
| 値で `false` | 同上 | E-IFFALSE | `t₃` |
| 値でない (`t₁ → t₁'`) | 帰納法の仮定 | E-IF | `if t₁' then t₂ else t₃` |

- どの場合も `t` に使える評価規則がある。つまり `t` は 1 歩進める。これで「値であるか、進める」の右側が成り立つ
- 示しているのは**次の 1 歩があること**だけ。値になるまで評価することは、進行は主張しない (値に着くかは正規化性という別の性質)。`t` 自体は `if` なので値にならない
- 型が効く場所は 1 行目と 2 行目。`t₁` が値でも、`0` のように `true` / `false` でない値だと、E-IFTRUE も E-IFFALSE も使えず行き詰まる。`t₁ : Bool` と標準形補題が、その場合を消している
- T-SUCC、T-PRED、T-ISZERO も同じ形 (部分式が進めば E-SUCC など、値なら標準形補題で形が決まって規則が使える)。本は T-ISZERO を「同様」で済ませている

### 定理 8.3.3 (保存) を噛み砕くと

> `t : T` かつ `t → t'` ならば、`t' : T`

- 型が付いている項は、1 歩評価しても、型が付いたままで、しかも**同じ型** `T` のまま
- 例: `if (iszero 0) then 0 else (pred 0)` は、E-IF、E-IFTRUE と進んでも、どの段階も `Nat`
- 保証しているのは、評価の途中で型が崩れないこと。`Nat` の項が `Bool` になったり、型が付かなくなったりしない
- 進行とのセット: 進行は「次の 1 歩がある」、保存は「次の項にも型が付く」。繰り返すと、型が付いた項は最後まで行き詰まらない
- 「同じ型」は、この言語だから言える。部分型を持つ体系では型が小さくなることがある (脚注 3)

### 保存の証明

- 方針: `t : T` の導出に関する帰納法。帰納法の仮定は「部分導出 `s : S` について、`s → s'` なら `s' : S`」。導出の最後の規則で場合分けする (本は一部だけ書き、残りは「同様」で省略)
- 場合分けは 2 段。1 段目は型付けの導出の最後の規則 (T-TRUE、T-IF など)、2 段目は `t → t'` の導出の最後の評価規則 (E-IFTRUE など)。Lean なら `cases` を `Typing`、`Step` の順に 2 回重ねる形
- **基底 (T-TRUE、T-FALSE、T-ZERO)**: `t` が値なので進めず、仮定 `t → t'` が成り立たない。「`P` ならば `Q`」の `P` が偽なので、命題は自明に成り立つ (`t'` が存在しないので `Q` には意味がない)
- **T-IF**: 前提 `t₁ : Bool`、`t₂ : T`、`t₃ : T` が手に入る。`if` に当てはまる評価規則は E-IFTRUE、E-IFFALSE、E-IF の 3 つ

| 進み方 | `t'` | `t' : T` の示し方 |
|---|---|---|
| E-IFTRUE | `t₂` | 前提の `t₂ : T` がそのまま結論。帰納法の仮定は不要 |
| E-IFFALSE | `t₃` | 同様 (本は省略) |
| E-IF (`t₁ → t₁'`) | `if t₁' then t₂ else t₃` | 帰納法の仮定を `t₁ : Bool` の部分導出に当てて `t₁' : Bool`。`t₂ : T`、`t₃ : T` と合わせて T-IF を再適用 |

- 保存の証明の肝は E-IF。部分式 (条件) の保存から、組み直した `if` 全体の保存を作る
- T-IF が `then` と `else` に同じ型 `T` を要求するから、E-IFTRUE と E-IFFALSE のどちらで進んでも `T` が付く
- 進行と違い、保存の T-IF では標準形補題を使わない (型の付け直しだけで済む)
- T-SUCC など、残りは同じ形

### 安全性 (健全性) = 進行 + 保存 の言い直し

型が付いた**すべての項**について、(1) 値であるか、1 歩進める (進行)、(2) 進んだ後にも同じ型が付く (保存) の 2 つが成り立つ。この 2 つが成り立つ型システムを、安全 (健全) という。

- 性質の持ち主は、個々の項ではなく**型システム** (型付け規則と評価規則の組)。「この型システムは、型付きのどんな項に対しても進行と保存が成り立つか」を問う。TS なら「TS の型システムは健全か」
- 保存は「型が一致する」ではなく、「進んだ後の項に**同じ型が付く**」
- 保存定理の別名は主部簡約 (subject reduction)。`t : T` を 1 つの文と見て、主語 `t` を簡約しても文の正しさが保たれる、という意味。逆向き (`t → t'` かつ `t' : T` なら `t : T`) は主部展開で、演習 8.3.6 (未解答)
- TS で壊れる側 (計画の穴 1〜7 につなげる読み。Effective TypeScript を読んで確かめる): 進行が壊れる例は `undefined.toFixed(1)` のような `TypeError`、保存が壊れる例は `string` と型が付いた値が実行時に `undefined` になる場合

### 型システムの健全性は証明できるか

- 証明できる。Ch 8 の証明は、型が付く項を**全部**、導出の最後の規則で場合分けして示している。規則に穴があれば、その規則の場合分けで証明が詰まる。「健全な項だけが選ばれて健全に見える」ことは起きない (見ているのは項ではなく規則全体)
- 手順は Lean などで形式化しても同じ。項、`Typing`、`Step` を帰納型で定義し、進行と保存を `Typing` に関する帰納法で証明する。規則を間違えると、その場合の証明が閉じない
- 証明が保証するのは**規則で書かれたモデル**の健全性だけ。隙間が 3 つある
  1. 規則と実装の間: モデルが健全でも、チェッカー (tsgo) の実装にバグがあれば不健全
  2. 規則と実際の実行の間: 評価規則が本物の JS の挙動を写している、という仮定が要る
  3. 形式化のしかた: 脚注 4 のとおり、小ステップか大ステップかで保存が成り立つか変わる
- 小さい言語 (真偽値と数) の進行・保存は、Software Foundations (Coq/Rocq) の型の章にある例とほぼ同じ (記憶ベース、題名と章は未確認)

### 形式化すると何ができるか

TS を完全に形式化すれば、健全かどうかを証明で確かめられる。健全でなければ、その箇所が証明の失敗として見える。健全にするには、受け入れるプログラムを絞るか、実行時チェックを足す。

- 形式化は、健全かどうかを**判定できる**ようにする作業。健全にする作業ではない。TS を形式化して証明を試みると、穴 1〜7 の場所で証明が閉じないはず (予想)
- スーパーセット (受け入れるプログラムを増やす) では健全になりにくい。健全にする方向は 2 つ
  - サブセット: 穴の原因になる機能を禁止する (tsz の Sound Mode、計画のパッチ)
  - 実行時チェックを足す: 型が崩れうる箇所で実行時に検査する (Safe TypeScript、記憶ベース)
- 証明されても残る隙間: モデルが本物の JS の挙動と合っているか、チェッカーの実装がモデルと合っているか
- 計画は、証明ではなく実プロジェクトでの壊れ方の**実測**で穴を見るアプローチ

### 完全に形式的な意味論を持つ言語 (記憶ベース、未確認)

- 形式的な定義がある: Standard ML (言語の定義が型付け規則と評価規則で書かれている)、WebAssembly (公式仕様が形式的、型安全性を定理証明支援系で検証した研究がある)、CompCert の C (C の部分集合を Coq で形式化)、CakeML (ML 系、コンパイラの正しさを HOL4 で検証)
- 部分的・研究段階: JavaScript (ECMAScript 仕様は擬似コードの準形式的なもの。JSCert や K Framework 版などの形式化研究はあるが仕様そのものではない)、Rust (公式な形式意味論はない。RustBelt が核を証明)、Haskell (中間言語 Core は形式化されているが表面の言語全体ではない)
- TS には公式な形式意味論がない。部分集合の研究として Safe TypeScript (実行時チェックを足して健全にした) を覚えているが、未確認
- 傾向: 形式的な定義があるのは、最初から設計に数学者が入った言語 (SML、Wasm) と、検証のために作られた部分集合 (CompCert、CakeML)。実用が先で後から仕様を整えた言語 (JS、TS) は形式化が追いついていない。TS が健全性を目標にしない背景と関係しそう (設計意図 #9825 などで確かめる)

### 質疑を通した結論

- **逆転補題 (補題 8.2.2)**: 項に型が付いているなら、項の形から、その型と部分式の型が決まる。型付け規則を結論から前提へ逆に読んだもの。例: `succ t₁ : R` なら `R = Nat` かつ `t₁ : Nat`。`if t₁ then t₂ else t₃ : R` なら `t₁ : Bool`、`t₂ : R`、`t₃ : R`
  - 「型が付いている」とは、型付け規則から導出木が作れたこと (Lean なら `Typing t T` の証明項がある)
  - 型推論 (型変数を制約で解く話) ではない。この言語には変数も注釈もなく、部分式の型から全体の型を計算するだけ
  - 使いどころ: 本の文面で名前つきで使われるのは、標準形補題 8.3.1 の証明だけ (`Bool` 型の値から `0` と `succ nv` を除くのに、補題の (4)・(5) を使う)。進行・保存の証明は導出に関する帰納法で、導出の最後の規則で場合分けするので、T-IF の前提 (`t₁ : Bool` など) は規則の形から直接手に入る。補題は経由しない。補題が要るのは、導出ではなく項と型の組だけが与えられているとき
- **進行の証明**: `t : T` の導出に関する帰納法。値になる規則 (T-TRUE など) は自明。部分式を持つ規則は、部分式に帰納法の仮定を当てる
  - 部分式が進めるなら、全体も進める (E-IF、E-SUCC など)
  - 部分式が値なら、その型と標準形補題で値の形が決まり、全体を進める規則が見つかる (例: `pred t₁` で `t₁ : Nat` かつ値なら `0` か `succ nv`。E-PREDZERO か E-PREDSUCC が使える)
  - 型が効く場所はここ。`t₁ : Nat` と分かっているから `pred false` のような項は来ない
- **保存の証明**: 1 歩進んだ前後を比べる。導出の最後の規則から分かる部分式の型を使って、進んだ先の項に型を付け直す。T-IF が `then` と `else` に同じ型 `T` を要求するのは、E-IFTRUE と E-IFFALSE のどちらで進んでも型が `T` のままになるため
- **型付け規則と評価規則は別物**: 型付け規則は「型が付くか」、評価規則は「どう進むか」。進行・保存は、この 2 つをつなぐ定理
- **TS の tsgo との対応** (`checkConditionalExpression`、checker.go:11193 を確認): 部分式を再帰で検査して型を得て、そこから全体の型を作る形は T-IF と同じ。ただし T-IF は `then` と `else` が同じ型であることを要求するが、tsgo は 2 つの型のユニオンにする (`b ? 0 : "a"` は TAPL では型なし、TS では `0 | "a"`)

## 2. Effective TypeScript 項目 7

読んだ日: 2026-11-09

### 項目 7: 型を値の集合として考える

**主張**: 型を「値の集合 (ドメイン)」として考えると、TS の型の振る舞いが一貫した見方で説明できる。型チェッカーのやっていることの多くは、ある集合が別の集合の部分集合かどうかの判定。

- 実行時、変数は 1 つの値を持つ。型チェック時、変数は「ありえる値の集合」(ドメイン) を持つ。`number` は全数値の集合
- TS の用語と集合論の用語の対応 (表 2-1)

| TS | 集合 |
|---|---|
| `never` | 空集合 (ボトム型) |
| リテラル型 | 1 要素の集合 |
| 値が `T` に代入可能 | 値 ∈ T |
| `T1` が `T2` に代入可能、`T1` が `T2` を拡張する | `T1` ⊆ `T2` |
| `T1 \| T2` | 和集合 |
| `T1 & T2` | 積集合 |
| `unknown` | 全体集合 (トップ型) |

- 「`A extends B`」は「`A` は `B` の**部分集合**」と読む。「拡張」は構造 (プロパティが増える) の見方から来た言葉で、集合 (値) の見方では逆に**狭くなる**。`Vector3D` は `Vector1D` より条件が多いので値の集合は小さい。「継承する」と読むと混乱する (`K extends string` は「ドメインが `string` の部分集合なら何でもよい」)
- 型は階層ではなく、重なりを持つ集合 (ベン図)。`string | number` と `string | Date` はどちらも他方のサブタイプでないが、`string` で重なる
- オブジェクト型は、追加のプロパティを持つ値も含む。`Person & Lifespan` は空ではなく、両方のプロパティを持つ値の集合。`keyof (A & B)` = `keyof A | keyof B`、`keyof (A | B)` = `keyof A & keyof B`
- 型を集合で考えると、配列とタプルの関係も分かる。`number[]` は `[number, number]` の部分集合ではないので代入できない。TS はタプルを `{0, 1, length: 2}` としてモデリングするので、3 要素のタプルも 2 要素のタプルに代入できない
- 訳者補記の `triple` → `double` の例: 部分集合でない代入を許すと、型と実行時の値が食い違う (`numNumStr[2]` の型は `"string"`、値は `3`)。本文の「部分集合でないから代入できない」の理由づけの例示。TS はこの代入を許さない
- TS は型の等価性をほとんどチェックしない。同じ集合を持つ型は同じ型 (意味的に違う型がたまたま同じドメインを持つ場合を除く)
- すべての集合が TS の型で表せるわけではない。「全整数」や「`x` と `y` だけを持つオブジェクト」を表す型はない。`Exclude<number, 0>` が `number` になるのは、`Exclude<T, U> = T extends U ? never : T` が、ユニオンのメンバーのうち `U` の部分集合のものを捨てるだけで、`number` 単体には `0` を抜く機会がないため
- 集合の見方は、値をイミュータブルと考えたときに最もうまく機能する。`Lockbox` と `ReadonlyLockbox` はドメインが同じだが挙動は違う。「型とは値の集合であり、かつそれを使って何ができるか」という補足がある

### TAPL との突き合わせ

- 計画の「項目 7 の定義 = すべてのシンボルについて、実行時の値が静的型のドメインの中にあること」は、**本文からは確認できなかった**。読んだ範囲に、この一文も「健全性」という語もない。項目 7 は健全性の定義を直接与える章ではなく、「型 = 値の集合」という見方を与える章
- 保存との結びつけは、私たち (読み手) の解釈: 型をドメインと見ると、「実行時の値がそのドメインに入っている」ことが保存に当たる。訳者補記の例は、部分集合でない代入を許すと値がドメインの外に出る (標準形補題が壊れる) ことを示している
- 計画の穴 3 (配列の共変、可変な参照は不変) につながるかもしれない点: 「値がイミュータブルなときに集合の見方が最もうまく機能する」という本の注意。読んで確かめる

### #9825 不健全性の扱い方の議論

読んだ日: 2026-11-09 (起票者の本文と、TS チームのコメント 8 件 (#4、#5、#11、#13、#16、#19、#22、#31) を読んだ。全 47 件のうち残りは未読。ラベルは Discussion、2016-07 起票、2024-02 クローズ)

起票者 (henryptung) の問い: TS は不健全性を「直すべきもの」と考えているか。"By Design" / "Design Limitation" で閉じられる issue が多いので、長期チケットを残す、警告フラグを足す、何もしない、のどれを選ぶのか。

原文のリンク (コメント番号は 0 始まり。URL は取得した JSON の値):

- mhegazy #4 (2016-07-20): https://github.com/microsoft/TypeScript/issues/9825#issuecomment-233843817
- RyanCavanaugh #5 (2016-07-20、三角形): https://github.com/microsoft/TypeScript/issues/9825#issuecomment-234115900
- RyanCavanaugh #16 (2017-06-05、JS の実行時の性質): https://github.com/microsoft/TypeScript/issues/9825#issuecomment-306272034
- RyanCavanaugh #22 (2017-12-12、健全性は代用指標): https://github.com/microsoft/TypeScript/issues/9825#issuecomment-350921122

TS チームの回答 (mhegazy = #4、RyanCavanaugh = #5 ほか):

- **健全性は設計目標ではない** (Ryan #5): 健全性・使いやすさ・複雑さは**トレードオフの三角形**で、「健全で、単純で、有用な型システムは存在しない」。例は穴 3 と同じ `Animal[]` への `push`。3 つの解がある
  - 単純・使える・不健全 = 今の TS
  - 単純・健全・使えない = サブタイプ置換を全部拒否 (`Node#addChild` が `Node` しか受けなくなる)
  - 健全・使える・単純でない = ミュータビリティの注釈 (C++ の `const`、C# の `in` / `out`)。`const` 正しさは感染するので、すべての `.d.ts` が変更の有無を正しく書く必要がある。「何が変更か」の合意も難しい
- 速度も理由に挙がる: 健全に近づける代わりに、コンパイラが 10 倍・100 倍遅くなる場合がある
- ただし Ryan #13 は「デフォルトの立場は soundness over completeness でもある」とも言う。`number | string` に `substr` を呼ばせたり、`Base` を `Derived` の代わりに渡させたりはしない。不健全な点は、意図的に選んだ限られた箇所
- **JS の実行時の性質が健全化を妨げる** (Ryan #16): getter は呼ぶたびに違う値を返せる。`valueOf` / `toString` は何でもできるので `x + y` の型が非決定的になりうる。`delete` の副作用は型で記述しにくい。配列は疎になれる。「JS 構文の上に完全に健全な型システムを作るのは fool's errand」。やりたいなら、PureScript のように、健全に型付けできない JS の構文を捨てる言語を作る
- **健全性は目的の代用指標** (Ryan #22): 型システムは正しいプログラムを書くための道具で、証明可能な健全性はその代用品。JSON を読む時点で型キャストが要り、キャストを許せば、最終的な健全性は、プログラマがキャストを正しく書くかに依存する。TS コンパイラ自身の最近のバグはキャストの誤りが多く、キャストなしの不健全性が原因のものは月に 1 回程度。TS と Flow を比べた論文では、Flow の少し厳しい健全性でだけ見つかったバグはゼロだった (論文は未確認)。「JS として自然に書けるなら 100% の健全性は無理なので、表現力を足して、起こりうる誤りを捕まえるのが最善」
- **設計は実測で決めた** (mhegazy #4): 実装してみて、実コードのエラーの何割が本物のバグかを見て決めた。「純粋に良いと思った変更が、実コードで試すとそうでなかったことが多い」。厳密な科学ではない、とも言っている。意図的な設計判断として、引数の bivariance、引数の少ない関数の代入、非 `void` の `void` への代入、`this` が `any`、型アサーション (上方・下方キャスト)、`any` の挙動を挙げる
- **モードを分けたくない** (mhegazy #4): 型システムの振る舞いを変えるフラグは避けてきた (ほとんどのフラグはチェックの追加かエラーの抑制)。理由は、オプション疲れと、言語を「モード」で分裂させないため。`--strict: level3` / `level5` のような段階は、何が strict で何が pedantic か不明なので見送った (#274)。tighten 系のフラグ (`noImplicitAny`、`strictNullChecks`) は「移行期」のもので、全員が最終的に使うべきもの、という位置づけ
- 「By Design」で閉じるのは、設計を変える予定がないから (開いていると変える意図があるように見える)。無視しているわけではない (mhegazy #4)
- Ryan #19: Flow も完全に健全ではない。配列の変更の扱いが弱く、`arr.sort()` の後に `arr[0].substr(0)` が実行時に落ちる例は、TS ではエラー、Flow ではエラーにならない

計画との関係 (読み手の解釈):

- Ryan の「3 つ目の解」(ミュータビリティの注釈) は、穴 3・穴 7 で `readonly` を型で追う方向と一致する
- 「`.d.ts` が正しく書かれているか」の指摘は、計画の「.d.ts の信頼問題」と同じ
- 「実コードで試して決めた」は、計画の「実プロジェクトでの壊れ方を量で実感する」と同じ発想

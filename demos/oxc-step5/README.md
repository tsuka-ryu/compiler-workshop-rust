# oxc Session 5.1 デモ: `as` / `satisfies` の「消せない」問題 — どういう場合にバグっていたか

[reading-oxc-ts.md](../../docs/reading-oxc-ts.md) の 5.1 / `parse_binary_expression_rest` (`js/expression.rs:1322`) の
`last_operand_precedence`。TypeScript#63527 → typescript-go#4192 → oxc#22986 の修正が、何を防いでいるかの実測。

## 何がバグだったのか (先に結論)

**TypeScript のパース自体は正しかった** (今も同じ)。問題は、**型を空白に置き換えるだけで JS にする素朴な除去**
(Node の type stripping や ts-blank-space のような実装) と、`erasableSyntaxOnly` (「消すだけで JS になる構文だけ許す」
オプション) の間にあった:

```ts
1 + 1 as number / 2;
```

| 見方 | 結果 |
|---|---|
| tsc の読み方 | `((1 + 1) as number) / 2`。出力 `(1 + 1) / 2` = **1** |
| 素朴な除去 (`as number` を空白にするだけ) | `1 + 1           / 2` = `1 + (1/2)` = **1.5** ← 意味が変わる |
| tsc 6.0.3 の `erasableSyntaxOnly` | **エラーを出さない** ← これが「バグ」 |

`erasableSyntaxOnly` を付けて「消すだけで動く」つもりでも、この形だけ消すと別の値になり、気づけなかった。

## なぜ `as number` の後ろの `/ 2` が `(1 + 1)` 全体にかかるのか

`as` の優先順位は関係演算子 (`<` `>` など) と同じで、`+` や `/` より**低い**。パーサーは次の順で読む
(`parse_binary_expression_rest` の `loop`):

1. `1` を読む。`+` を見て右辺を読む。右辺を読むとき `as` は `+` より弱いので、右辺は `1` で止まる → `1 + 1`
2. ループに戻って `as` を見る (このときの最低ラインは、外側の文脈のもの = 一番低い) → 消費。右側は式ではなく**型** (`parse_ts_type`) を読む → `(1 + 1) as number`
3. ループに戻って `/` を見る。`/` は最低ラインより強いので、**`(1 + 1) as number` を左辺として** 消費 → `((1 + 1) as number) / 2`

`as number` を消すと 3 の左辺が `1 + 1` でなくなり、`1 + 1 / 2` は `/` が先に結合してしまう。

## 修正: `as T` の後ろに「直前の演算子より強い演算子」が続いたら止める

`as` / `satisfies` を読んだ直後、後ろの演算子が、**この左辺を作った二項演算子 (`##`) より強い**なら、そこで読むのを止める。
`/ 2` は宙に浮いて**パースエラー**になり、書き手は括弧を付けて意図を明示する必要が出る。

## 実測 (`compare.js`、出力は `results.txt`)

tsc は 6.0.3 (issue が確認したバージョン = 修正前の挙動)、oxc は rev `1aa5ec11ce` (修正 #22986 を含む)。
② は `as T` / `satisfies T` の文字を空白にするだけの除去をして、その JS を実行した値。

| デモ | 入力 | ① tsc の出力 (値) | ② 空白で消した値 | tsc `erasableSyntaxOnly` | ③ oxc |
|---|---|---|---|---|---|
| demo1 | `1 + 1 as number / 2` | `(1 + 1) / 2` (1) | 1.5 ★食い違う | エラーなし | **エラー** (`/` で止まる) |
| demo2 | `1 + 1 as number * 2` | `(1 + 1) * 2` (4) | 3 ★食い違う | エラーなし | **エラー** (`*` で止まる) |
| demo3 | `1 as number * 2` | `1 * 2` (2) | 2 一致 | エラーなし | OK |
| demo4 | `1 * 1 as number + 2` | `1 * 1 + 2` (3) | 3 一致 | エラーなし | OK |
| demo5 | `1 + 1 as any as number * 2` | `(1 + 1) * 2` (4) | 3 ★食い違う | エラーなし | **エラー** (連鎖でも元の `+` と比べる) |
| demo6 | `1 >> 1 as number + 2` | `(1 >> 1) + 2` (2) | 0 ★食い違う | エラーなし | **エラー** (`+` で止まる) |

## 直し方: 括弧を付けて意図を明示する (demo11-13)

元の `1 + 1 as number / 2` は `(1 + 1) / 2` と `1 + (1 / 2)` のどちらの意味か曖昧なので、エラーにして書き手に選ばせる:

| デモ | 書きたい意味 | 書き方 | ① tsc の出力 (値) | ② 空白で消した値 | ③ oxc |
|---|---|---|---|---|---|
| demo11 | `(1 + 1) / 2` | `(1 + 1) as number / 2` | `(1 + 1) / 2` (1) | 1 一致 | OK |
| demo12 | 同上 | `(1 + 1 as number) / 2` | `(1 + 1) / 2` (1) | 1 一致 | OK |
| demo13 | `1 + (1 / 2)` | `1 + (1 as number) / 2` | `1 + 1 / 2` (1.5) | 1.5 一致 | OK |

`(1 + 1) as number / 2` (demo11) が通るのは、`(1 + 1)` が括弧付きの 1 つの式として読まれ、ループの中で二項演算子を
消費していない (`last_operand_precedence` が `None` のまま) ため。

**読み取れること**:

- **食い違うのは、「`as` の直前の二項演算子より強い演算子が後ろに続く」ときだけ** (demo1・2・5・6・9)。oxc は、ちょうどこの
  5 件をエラーにして、残り (demo3・4・7・8・10) は通す。「食い違う」と「oxc がエラーにする」が完全に一致している
- **demo4・demo10** が境目を示す: 後ろの演算子が直前と**同じか弱い**ときは消しても意味が変わらないので通す
  (demo4: `*` の後の `+` は弱い、demo10: `-` の後の `-` は同じ強さ)
- **demo6** (`>>` と `+`) は、`+` が `>>` より強いので食い違う。「足し算と掛け算」に限らない
- **demo5** (連鎖): 追跡している優先順位を `as` で書き換えないので、`as any` を挟んでも元の `+` と比べ続けて止まる
- **tsc 6.0.3 の `erasableSyntaxOnly` は、全ケースでエラーなし** (修正前の挙動)。これが issue の本題だった
- **tsc は全ケースを正しく読んでいる** (① の出力は意図どおり)。食い違うのは、②の素朴な除去だけ
